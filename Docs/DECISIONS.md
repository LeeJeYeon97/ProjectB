## DEC-001 — ChatGPT 설계 / Codex 구현·검증 역할 분리

- **날짜/상태:** 2026-10-26, 사용자 확정.
- **결정한 내용:** ChatGPT가 기획·설계·밸런스·로드맵·구현 명세를 맡고 Codex가 코드 분석·구현·검증·문서 갱신을 맡는다. 최종 중요 규칙은 사용자가 확정한다.
- **결정 배경:** ChatGPT가 Unity 프로젝트를 직접 실행하지 않아도 GitHub의 문서로 현재 상태를 파악해야 한다는 이번 요청.
- **선택한 방식:** 프로젝트 루트 AGENTS와 Docs의 GAME_DESIGN/ARCHITECTURE/DEVELOPMENT_STATUS/DECISIONS/BACKLOG를 공통 문맥으로 사용한다.
- **고려했던 대안:** 사용자 요청에 대안 비교 기록 없음. 채팅만 사용하거나 별도 위키를 사용하기로 검토했다는 사실을 추정하지 않는다.
- **선택 이유:** 사용자 명시 목적은 정확한 현재 상태 공유, 유지보수, AI 사이 문맥 전달 효율이다.
- **향후 확장 시 제약사항:** 문서로 런타임 검증을 대신할 수 없다. 제안/확정/코드 관찰을 구분하고 기준 SHA를 전달해야 한다. Git 커밋·Push는 승인 범위 안에서만 수행한다.
- **근거:** 이번 사용자 요청, [AGENTS](../AGENTS.md).

## DEC-002 — 기존 코딩 규칙과 Core 매니저 보호 유지

- **날짜/상태:** 2026-10-26에 재기록, 원래 도입 날짜 확인 필요. 기존 사용자 규칙을 유지한다.
- **결정한 내용:** 한국어 주석, 쉬운 명명, 재사용성, SOLID/높은 응집도·낮은 결합도, 한 시스템의 Manager 제한, UI 베이스/enum Bind/프리팹 요소 사전 제작, Define enum 집중, 함수 배치와 region 규칙을 적용한다. Core 매니저 수정은 사전 사용자 승인을 받는다.

- **선택한 방식:** 기존 14개 규칙을 보존하고 작업 전·후 및 검증·문서 관리 규칙을 추가했다.
- **고려했던 대안:** 기존 규칙을 정할 때 검토한 대안은 기록 없음.
- **선택 이유:** 사용자가 지정한 프로젝트 제약을 계속 적용한다. 개별 규칙의 최초 기술적 선택 이유는 확인 필요다.
- **향후 확장 시 제약사항:** 기존 위반 코드가 새 위반의 근거가 되지 않는다. 전역 Managers 구조 개선을 이유로 Core를 임의 수정하지 않는다. 변경 필요 파일/영향을 먼저 분석한 뒤 승인 범위를 확인한다.

## DEC-003 — 가구 자유 위치 배치와 90도 회전

- **날짜/상태:** 2026-10-26에 기존 문서에서 이관 기록. 원래 결정일/승인 이력 확인 필요. 기존 설계 의도를 보존한다.
- **결정한 내용:** 위치는 연속 월드 좌표, 방향은 90도 단위로 조작한다. 모바일에서는 이동과 확정을 분리하고 별도 배치 버튼을 사용한다.
- **결정 배경:** 기존 「가구 배치 최종 설계」는 3D 바 운영, 모바일 조작, 손님·직원 동선과 기능 가구의 연결을 설명한다.
- **선택한 방식:** 자유 위치 + 90도 회전, 영역/겹침 재검사, 별도 확정/취소, 배치 중 플레이어 이동 차단. 의자 하나부터 검증하고 확장한다.
- **고려했던 대안:** 문서에서 기존 격자 반올림과 선택적 미세 스냅을 비교한다. 미세 스냅은 후속 편의 기능으로 남긴다. 별도 실험 결과는 없다.
- **선택 이유:** 문서에 명시된 이유는 위치 자유도를 주면서 방향과 조작 규칙을 단순하게 유지하기 위해서다.
- **향후 확장 시 제약사항:** 실제 가구만 좌석 시스템에 참여하고 사용/예약 좌석의 이동을 제한해야 한다. 현재 코드는 네 모서리 바닥 검사이며 전용 금지 영역·통로 보호가 없다. 기존 설계의 설치 시 차감과 현행 선구매 재고 소비의 차이는 별도 결정이 필요하다.
- **근거:** [가구 배치 최종 설계](../Assets/09_Plan/가구_배치_최종_설계.md), [현행 가구 구현](../Assets/01_Scripts/Content/Furniture/FurniturePlacementController.cs).

## DEC-004 — 레시피 데이터로 메뉴 구분하는 현행 구현

- **날짜/상태:** 2026-10-26 관찰 기록. 원래 결정일/승인 이유 확인 필요. 미래 기획 확정 기록이 아니다.
- **결정한 내용:** 현행 코드는 메뉴를 ItemType.Menu로 묶고 FoodRecipeData 참조로 구체적인 음식을 구분한다.
- **결정 배경:** FoodRecipeData에 기계·재료·시간·완성품·가격이 있고, ItemController.MenuRecipe 및 StackingSystem의 레시피 비교가 존재한다. b4fd92b에서 관련 클래스가 변경되었다.
- **선택한 방식:** MenuMachine의 recipe와 완성품 ItemController.MenuRecipe가 같은 에셋인지 검사하고, 스택도 같은 recipe만 허용한다. 매장 공용 IngredientManager가 레시피 재료를 확인하고 주문 수량을 예약한다.
- **고려했던 대안:** 코드 변경 이전 형태는 Git 이력에서 볼 수 있으나 당시 어떤 대안을 검토했는지 확인되지 않았다.
- **선택 이유:** 기록된 이유 없음. 데이터 확장이 목적이었다고 단정하지 않는다.
- **향후 확장 시 제약사항:** 당시에는 직원 서빙·퀘스트·가격에 레시피 식별이 끝까지 전달되지 않았다. 서빙과 가격은 DEC-010으로 연결했으며, 퀘스트의 레시피별 목표(ISS-006)와 저장용 안정 ID 필요 여부는 남았다.
- **근거:** [FoodRecipeData](../Assets/01_Scripts/Data/FoodRecipeData.cs), [MenuMachine](../Assets/01_Scripts/Content/InteractObject/MenuMachine.cs), [StackingSystem](../Assets/01_Scripts/Content/Player/StackingSystem.cs).

- **날짜/상태:** 2026-10-26, 이번 사용자 요청으로 확정.
- **결정한 내용:** 작업 결과에 따라 관련 문서만 자동 갱신하고 코드 구현 완료와 실제 동작 검증 완료를 구분한다.

- **선택한 방식:** 상태·버그는 DEVELOPMENT_STATUS, 구조는 ARCHITECTURE, 게임 규칙은 GAME_DESIGN, 근거 있는 결정은 DECISIONS, 작업은 BACKLOG에 기록한다. 이슈/작업 ID와 저장소 상대 링크를 사용한다.

- **선택 이유:** 실제 코드와 확인한 사실을 기준으로 유지하고, 문서 중복·긴 작업 일지를 줄이라는 사용자 요구를 따른다.
- **향후 확장 시 제약사항:** 자동 갱신은 Codex가 승인된 작업을 수행할 때의 절차다. 백그라운드 동기화 서비스·CI·커밋 훅을 설치한 것은 아니다. 기준 SHA는 실제 코드 스냅샷이며 미래 문서 커밋을 추정하지 않는다.
- **근거:** [AGENTS](../AGENTS.md), [상태 문서의 검증 구분](DEVELOPMENT_STATUS.md).

## DEC-006 — 재고 부족 손님의 좌석 점유

- **날짜/상태:** 2026-10-26, 사용자 확정. 주문 시점과 재시도 방식은 2026-10-27 DEC-013으로 대체되며 좌석 점유 규칙은 유지.
- **결정한 내용:** 주문 가능한 재료가 없더라도 손님은 퇴장하지 않는다. 재고가 보충될 때까지 해당 좌석을 계속 점유한다.
- **결정 배경:** 사용자는 재고 부족 동안 손님이 자리를 선점하는 것이 게임의 기믹이라고 지정했다.
- **선택한 방식:** 재고가 충분한 레시피가 없을 때는 주문과 직원 서빙 작업을 만들지 않고 착석 상태를 유지한다. `IngredientManager.AddIngredients`의 재고 변경 알림으로 손님이 주문을 다시 시도한다.
- **고려했던 대안:** 재고 부족 시 손님을 결제 없이 퇴장시키고 좌석을 청소 상태로 바꾸는 초안이 있었으나 채택하지 않았다.
- **선택 이유:** 사용자가 지정한 핵심 플레이 규칙을 따른다.
- **향후 확장 시 제약사항:** 별도 대기 시간, 손님 이탈 조건, 보급 UI/경제, 재고 저장은 결정되지 않았다. 현재 재고는 런타임에만 유지된다.
- **근거:** [GAME_DESIGN의 재고 규칙](GAME_DESIGN.md), [IngredientManager](../Assets/01_Scripts/Managers/Content/IngredientManager.cs), [CustomerController](../Assets/01_Scripts/Content/Controller/CustomerController.cs).

## DEC-007 — 재료 정의 데이터의 저장 위치와 로드 방식

- **날짜/상태:** 2026-10-26, 사용자 확정.
- **결정한 내용:** 재료 ScriptableObject 데이터 에셋은 `Assets/10_Data` 아래에 두고, 재료 시스템은 Resources 폴더를 사용하지 않는다.
- **결정 배경:** 사용자가 재료 데이터에 종류·이름·가격·프리팹 필드를 추가하고 데이터 파일의 위치를 지정했다.
- **선택한 방식:** `Assets/10_Data/FoodIngredient`에 재료별 `IngredientCatalog` 에셋을 두고 Addressables의 `IngredientData` 라벨로 비동기 로드한다. `StartingAmount`는 각 데이터에 보관하고, 실행 중 수량은 IngredientManager가 관리한다.
- **고려했던 대안:** 다른 로드 방식의 사용자 검토 기록은 없다.
- **선택 이유:** 데이터 위치와 Resources 사용 제한이라는 사용자 지시를 따른다.
- **향후 확장 시 제약사항:** 새 재료를 추가하면 유효한 종류와 시작 수량을 설정하고 같은 Addressables 라벨을 지정해야 한다. 품질별 재고·가격 반영 규칙은 아직 결정되지 않았다.

## DEC-008 — 퀘스트 연출 완료 후 다음 목표 시작

- **날짜/상태:** 2026-10-26, 사용자 요청으로 확정.
- **결정한 내용:** 퀘스트 목표를 달성해도 진행바·완료·보상 표시 시간이 끝나기 전에는 다음 퀘스트를 화면에 띄우지 않는다.

- **선택한 방식:** QuestManager가 완료와 실제 보상 지급을 한 번 확정하고 UI_Quest의 연출 종료 알림을 기다린다. UI가 없거나 중간에 숨겨지면 다음 목표로 진행한다. 연출 시간은 UI_Quest에서 조절한다.
- **고려했던 대안:** 기존의 즉시 전환 방식은 완료 연출을 가리므로 유지하지 않았다.

- **향후 확장 시 제약사항:** 현재 보상 표시는 텍스트다. 별도 보상 효과를 추가하면 종료 알림 시점을 함께 조정해야 한다. 퀘스트 진행·완료 대기 상태의 저장은 아직 구현되지 않았다.

## DEC-009 — 공용 직원 프리팹과 후보별 데이터로 선택 고용

- **날짜/상태:** 2026-10-26, 사용자 확정 테스트 범위.
- **결정한 내용:** 현재 직원 외형을 분리하지 않고 기존 `Employee.prefab` 하나로 여러 후보를 고용한다. 후보별 능력치와 가능한 업무는 데이터로 바꿔 끼운다.
- **결정 배경:** 사용자가 원하는 직원을 고르는 고용 방식과 UI 구현을 요청했고, 외형 차이는 현재 우선순위가 아니라고 밝혔다.
- **선택한 방식:** `Assets/10_Data/Employee`의 `EmployeeData` 세 에셋을 Addressables `EmployeeData` 라벨로 읽는다. 메뉴 팝업의 미리 제작된 카드에서 선택해 고용하며 후보 ID당 실행 중 한 번만 허용한다. 가격 0은 이번 테스트를 위한 임시 값이다.
- **고려했던 대안:** 후보마다 별도 프리팹을 두는 방식은 이번 요청에서 사용하지 않는다. 다른 가격·저장 정책의 사용자 검토 기록은 없다.
- **선택 이유:** 공용 외형을 유지하면서 업무와 속도 차이를 바로 시험할 수 있고, 데이터 에셋 위치와 UI 사전 제작 규칙을 따른다.

## DEC-010 — 다른 메뉴 수락과 주문 레시피 기준 결제

- **날짜/상태:** 2026-10-27, 사용자 확정.
- **결정한 내용:** 주문과 다른 레시피의 메뉴도 수락하지만 리뷰를 감점한다. 같은 메뉴는 주문 레시피 `Pay` 전액, 다른 메뉴는 주문 레시피 `Pay`의 절반을 기본 결제액으로 사용한다.
- **결정 배경:** `ItemType.Menu`만 비교하던 서빙과 손님별 고정 `payAmount`는 여러 레시피를 구분하지 못했다.
- **선택한 방식:** `ItemController.MenuRecipe`와 주문 레시피 에셋 참조를 비교한다. 다른 레시피는 기존 리뷰 규칙대로 2점을 감점하며 절반 금액의 소수 부분은 버린다. 비메뉴와 레시피 참조가 없는 메뉴는 거부한다.
- **고려했던 대안:** 다른 메뉴를 거부하거나 실제 제공 레시피 가격을 결제 기준으로 삼는 방식은 이번 사용자 선택에서 채택하지 않았다.
- **선택 이유:** 사용자가 다른 메뉴 수락·리뷰 감점과 주문 레시피 가격 기준, 정상 메뉴 전액·다른 메뉴 절반을 직접 확정했다.
- **향후 확장 시 제약사항:** 현재 맥주 레시피 `Pay`는 0이다. 가격 밸런스와 레시피별 퀘스트 목표는 별도 작업이며, 이번 변경의 전체 씬 플레이 결과는 [DEVELOPMENT_STATUS](DEVELOPMENT_STATUS.md)를 따른다.
- **근거:** 이번 사용자 답변, [CustomerController](../Assets/01_Scripts/Content/Controller/CustomerController.cs), [SeatStation](../Assets/01_Scripts/Content/InteractObject/SeatStation.cs), [Counter](../Assets/01_Scripts/Content/InteractObject/Counter.cs).

- **근거:** 이번 사용자 지시, [GrowthManager](../Assets/01_Scripts/Managers/Content/GrowthManager.cs), [GrowthCatalog](../Assets/10_Data/GrowthCatalog.asset), [Addressables Data 그룹](../Assets/AddressableAssetsData/AssetGroups/Data.asset).

## DEC-012 — 범용 이동 코드와 프로젝트 성장 로직의 분리

- **날짜/상태:** 2026-10-27, 사용자 요청.
- **결정한 내용:** `ThirdPersonController`는 다른 프로젝트로 옮겨 쓸 수 있도록 성장·적재·프로젝트 공용 enum에 직접 의존하지 않는다.
- **결정 배경:** 사용자가 이동 컴포넌트의 재사용성을 위해 프로젝트 전용 의존성 제거를 요청했다.
- **선택한 방식:** 이동 속도는 범용 `MoveSpeed`로 받고, 선택적 화면 방향은 `ExtraMoveDirection` 함수로 받는다. 플레이어 성장 계산, `ScreenMoveInput`, 운반 애니메이션 연결은 `PlayerController`가 담당한다. 이동 모드 enum은 이동 컴포넌트 내부로 옮기되 기존 숫자 순서를 유지한다.
- **고려했던 대안:** 이동 코드에 `SetGrowthSpeedBonus`와 적재·화면 입력 컴포넌트 참조를 유지하는 방식은 단독 재사용 목적에 맞지 않는다.
- **선택 이유:** 이동 계산은 Unity의 CharacterController와 Input System만 사용하고 현재 게임의 규칙은 플레이어 코드에 남길 수 있다.
- **향후 확장 시 제약사항:** 다른 프로젝트에서는 Input System 패키지와 CharacterController가 필요하며, 외부 방향 입력은 필요한 경우에만 연결한다. 변경 후 컴파일·플레이 검증은 사용자가 진행한다.
- **근거:** 이번 사용자 요청, [이동 컨트롤러](../Assets/01_Scripts/Utils/ThirdPersonController.cs), [플레이어 컨트롤러](../Assets/01_Scripts/Content/Player/PlayerController.cs).

## DEC-013 — 재고가 없어도 주문을 먼저 확정

- **날짜/상태:** 2026-10-27, 사용자 정정으로 확정.
- **결정한 내용:** 재고가 없어도 손님은 활성 기계의 메뉴를 주문하고, 그 주문을 유지하며 재료가 들어올 때까지 좌석에서 기다린다.
- **결정 배경:** DEC-006 구현은 재고 부족 시 주문 자체를 미뤄 손님 말풍선에 메뉴가 나오지 않았다. 사용자가 주문을 먼저 하도록 정정했다.
- **선택한 방식:** `CustomerManager`는 재고와 무관하게 활성 기계의 레시피를 고른다. `CustomerController`는 주문과 말풍선을 확정한 뒤 재료 예약을 시도한다. 예약이 실패하면 주문을 바꾸지 않고 기다리며, 보충 또는 예약 해제 알림에 같은 레시피를 다시 예약한다. 예약 성공 후에만 직원 서빙 작업을 만든다.
- **고려했던 대안:** 재고가 들어왔을 때 메뉴를 처음 고르는 이전 방식은 이번 사용자 지시와 맞지 않아 대체했다.
- **선택 이유:** 재고 부족이 손님의 주문 표시와 좌석 점유를 막지 않으면서, 실제 제조는 확보한 재료만 사용하도록 유지한다.
- **향후 확장 시 제약사항:** 주문 메뉴는 기다리는 동안 자동으로 다른 메뉴로 바뀌지 않는다. 이번 변경의 컴파일·실제 플레이 검증은 사용자가 진행한다.
- **근거:** 이번 사용자 정정, [CustomerManager](../Assets/01_Scripts/Managers/Content/CustomerManager.cs), [CustomerController](../Assets/01_Scripts/Content/Controller/CustomerController.cs), [IngredientManager](../Assets/01_Scripts/Managers/Content/IngredientManager.cs).

## DEC-016 — 재료 배송과 창고 입고

- **날짜/상태:** 2026-10-29, 사용자 확정. 일부 플레이 검증 완료.
- **결정한 내용:** 초기 공용 용량 15, 물·면·소스 시작 재고 각 0. 시장은 어디서든 사용하며 재료는 문 앞에 즉시 배송하고 플레이어 또는 직원이 창고로 운반해 입고한다. 공용 재고가 가득 차면 주문을 막으며, 운반 중 공간이 없어지면 배송 지점에 반환한다. 재료끼리는 혼합 적재 가능하고 음식과 재료는 혼합하지 않는다. 제조는 공용 재고를 직접 이용한다.
- **선택한 방식:** 배송 관련 동작은 기존 IngredientManager가 맡는다. 최초 창고 활성화 시 공용 기본 용량 15가 적용되며 추가 창고의 추가 용량은 미확정이므로 현재 기본값 0이다. 직원 업무 enum에 재료 운반을 추가하고 기존 세 후보 모두에게 연결한다. 재료 외형은 임시 색상 상자다. 배송 영역에는 접근 가능한 물건만 표시하고 빈자리가 생기면 대기 물품을 순서대로 표시한다.
- **대안과 이유:** 구매 즉시 재고로 들어가는 현행 방식은 직접 운반·입고하려는 사용자 기획과 다르다.
- **제약:** 물품 인계·작업 취소·직원 이동·동시 입고·기존 예약 및 시장 구매는 함께 검증해야 한다. 현행 구현과 차이는 [DEV-024](BACKLOG.md)를 따른다.
- **근거:** 사용자 확정 기획, [IngredientManager](../Assets/01_Scripts/Managers/Content/IngredientManager.cs), [시장 UI](../Assets/01_Scripts/UI/Popup/UI_MenuPopup.cs).

## 앞으로 추가할 결정의 형식

새 DEC ID를 부여하고 날짜/상태, 결정 내용, 배경, 선택 방식, 실제 검토한 대안, 이유, 확장 제약, 근거를 기록한다. 사용자 확인 전에는 `제안` 또는 `확인 필요`로 표시한다. 기존 결정을 바꿀 때는 기존 항목에 대체 DEC ID를 연결하고 원래 이유를 보존한다.
